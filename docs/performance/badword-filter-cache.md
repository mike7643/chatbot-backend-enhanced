# 금칙어 필터 로컬 캐시 적용

## 1. 결과 요약

메시지마다 Redis에서 금칙어·허용어 전체를 읽고 Aho-Corasick 필터를 새로 만들던 구조를, 버전 키 비교 후 변경 시에만 다시 만드는 로컬 캐시로 바꿨다.

3회 측정 중앙값 (금칙어 1,000개, 허용어 100개):

| 지표 | 적용 전 | 적용 후 | 변화 |
| --- | ---: | ---: | ---: |
| 일반 메시지 1건 평균 | 879μs | 145μs | 83.5% 감소 |
| 일반 메시지 1건 p95 | 1,091μs | 178μs | 83.7% 감소 |
| 금칙어 메시지 1건 평균 | 1,601μs | 288μs | 82.0% 감소 |
| 메시지당 Redis 조회 | Set 2개 전체 (`SMEMBERS` × 2, 금칙어 발견 시 × 4) | 버전 키 1개 (`GET`) | |

## 2. 문제 상황

- `BadwordServiceImpl.checkBadWord()`는 메시지가 올 때마다 금칙어·허용어 Set 전체를 Redis에서 읽고 `BanWordValidator`(Aho-Corasick Trie)를 새로 만들었다.
- 금칙어가 발견되면 관리자 모듈에 기록을 보내기 위해 같은 작업을 한 번 더 반복했다.
- 금칙어 목록은 관리자가 바꿀 때만 달라지는데, 매 메시지마다 목록 크기에 비례하는 네트워크 전송과 Trie 생성 비용을 냈다.

## 3. 변경 내용

- 관리자 모듈: 금칙어·허용어 Set을 바꾼 뒤 `badword:version` 키를 증가 (커밋 후 리스너, 주기 동기화에서 실제 변경이 있을 때)
- 챗봇: `BanWordValidatorProvider`가 필터를 로컬에 보관
  - 메시지마다 버전 키만 조회하고, 버전이 같으면 캐시한 필터 사용
  - 버전이 바뀌면 Set을 다시 읽어 필터 재생성
  - 버전 증가가 누락되거나 키가 유실돼도 60초가 지나면 다시 생성
- Set을 먼저 갱신하고 버전을 나중에 올리므로, 새 버전을 본 챗봇은 항상 새 Set을 읽는다.

## 4. 측정 방법

- `BadwordFilterBenchmark` (`./gradlew benchmarkTest`, 기본 테스트에서는 제외)
- Redis 7 Testcontainers (로컬 Docker), 무작위 한글 금칙어 1,000개와 허용어 100개
- 워밍업 500회 후 3,000회 측정, 3회 실행 중앙값
- 적용 전 시나리오는 기존 코드와 같은 순서(Set 조회 → 필터 생성 → 검사)를 그대로 재현

## 5. 참고: 금칙어 수에 따른 검사 비용

같은 64자 메시지를 검사할 때, 단어마다 `contains`로 찾는 단순 탐색과 Aho-Corasick의 평균 비용 (3회 중앙값, μs):

| 금칙어 수 | 단순 탐색 | Aho-Corasick |
| ---: | ---: | ---: |
| 100 | 6.4 | 0.9 |
| 1,000 | 21.4 | 1.0 |
| 10,000 | 191.1 | 1.0 |

단순 탐색은 금칙어 수에 비례해 늘어나지만, Aho-Corasick은 메시지 길이에만 비례해 금칙어 수와 무관하게 약 1μs를 유지한다. 반대로 필터를 만드는 비용은 금칙어 수에 비례하므로, 필터를 한 번 만들어 재사용하는 이번 변경과 함께 써야 효과가 난다.

## 6. 한계

- 로컬 Docker의 Redis라 네트워크 지연이 매우 작다. 실제 서버 간 네트워크에서는 적용 전 비용(전체 Set 전송)이 더 커진다.
- 적용 후 남은 비용(약 140μs)은 대부분 버전 키 조회 왕복 시간이다.
- 챗봇 응답 전체 시간(LLM 호출, 초 단위)에 비하면 작은 구간이며, 이번 변경의 실익은 메시지마다 반복되던 Redis 전송량과 CPU 사용 제거다.
