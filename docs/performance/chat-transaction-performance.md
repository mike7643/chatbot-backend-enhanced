# Chatbot 장기 트랜잭션 성능 개선

## 1. 결과 요약

채팅 응답 로직에서 DB 조회·저장 이후 LLM(Gemini)와 내부 API 호출까지 하나의 트랜잭션으로 묶여 있던 구조를 개선했다. `generateReply()`의 외부 호출 구간에서는 트랜잭션을 열지 않고, Spring Data Repository의 짧은 DB 작업 단위에서만 트랜잭션을 사용하도록 경계를 축소했다.

동일 조건으로 개선 전후를 각각 3회 측정한 중앙값은 다음과 같다.

| 지표 | 개선 전 | 개선 후 | 변화 |
|---|---:|---:|---:|
| 전체 20건 완료 시간 | 4,342ms | 1,329ms | 69.4% 감소 |
| 처리량 | 4.606 req/s | 15.049 req/s | 3.27배 증가 |
| 평균 응답시간 | 2,781ms | 1,320ms | 52.5% 감소 |
| p50 | 2,259ms | 1,320ms | 41.6% 감소 |
| p95 | 4,342ms | 1,328ms | 69.4% 감소 |
| p99 | 4,342ms | 1,328ms | 69.4% 감소 |
| 성공/실패 | 20/0 | 20/0 | 오류 없음 |

## 2. 문제 상황

`ChatServiceImpl`에는 클래스 수준 `@Transactional`이 선언되어 있었다. 따라서 다음 흐름 전체가 하나의 트랜잭션으로 실행됐다.

1. 채팅방 조회
2. 사용자 메시지 저장
3. 금칙어 확인과 감정 분석
4. Gemini 응답 대기
5. 추천·사용자·요금제 등 내부 API 호출
6. 챗봇 메시지 저장

DB 작업 이후 느린 외부 응답을 기다리는 동안에도 트랜잭션과 JDBC 커넥션이 유지됐다. 운영 설정의 HikariCP 최대 크기는 5이므로 동시 요청이 5개를 넘으면 나머지 요청은 커넥션 반환을 기다리게 된다.

## 3. 성능 가설

> 외부 API 지연 자체는 제거할 수 없지만, 외부 응답을 기다리는 동안 DB 커넥션을 점유하지 않으면 요청들이 5개씩 직렬화되는 현상을 제거할 수 있다.

이를 검증하기 위해 외부 응답시간을 정확히 1초로 고정하고, 서로 다른 채팅방 20개에 요청을 동시에 보냈다. 서로 다른 채팅방을 사용했기 때문에 Redisson 채팅방 락 경합은 측정 결과에서 제외된다.

## 4. 테스트 환경

| 항목 | 설정 |
|---|---|
| 애플리케이션 | Spring Boot 3.5.0, Java 17 |
| DB | Testcontainers MySQL 8.4 |
| 세션·락 | Testcontainers Redis 7.4, 실제 Redisson/Redis 구현 |
| 커넥션 풀 | HikariCP 최대 5, 최소 idle 2 |
| 동시 요청 | 20개 |
| 채팅방 | 요청마다 서로 다른 채팅방 |
| 외부 지연 | Gemini 응답 1,000ms 고정 |
| 외부 의존성 | Gemini·감정 분석만 Mockito로 대체 |
| 반복 횟수 | 개선 전 3회, 개선 후 3회 |
| 측정 계층 | 실제 Spring 프록시와 JPA를 사용하는 서비스 통합 테스트 |

실제 Gemini를 부하 테스트하지 않은 이유는 네트워크와 모델 응답시간 변동을 제거하고, 트랜잭션 경계 변경만 독립 변수로 두기 위해서다.

## 5. 개선 전 결과

| 실행 | 완료 시간 | 처리량 | 평균 | p50 | p95 | p99 | 최대 active | 최대 pending |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 4,338ms | 4.610 req/s | 2,769ms | 2,250ms | 4,337ms | 4,337ms | 5 | 18 |
| 2 | 4,342ms | 4.606 req/s | 2,781ms | 2,259ms | 4,342ms | 4,342ms | 5 | 18 |
| 3 | 4,354ms | 4.593 req/s | 2,801ms | 2,298ms | 4,353ms | 4,353ms | 5 | 18 |

HikariCP의 5개 커넥션이 외부 호출 동안 점유되면서 20개 요청이 사실상 약 5개씩 네 번에 걸쳐 처리됐다. 외부 지연은 1초지만 마지막 요청의 p95/p99는 약 4.34초까지 증가했다.

## 6. 수정 내용

`ChatServiceImpl`의 기존 클래스 트랜잭션 정책은 다른 조회 메서드를 위해 유지하고, 채팅 응답 진입점만 다음과 같이 명시적으로 제외했다.

```java
@Override
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public ChatResponseDto generateReply(Long userId, Long chatRoomId, String message) {
    // 채팅 흐름 실행
}
```

변경 후 흐름은 다음과 같다.

1. `generateReply()`는 장기 트랜잭션을 생성하지 않는다.
2. Repository 조회·저장은 Spring Data가 관리하는 짧은 트랜잭션에서 실행된다.
3. Gemini와 내부 API 응답을 기다리는 동안 JDBC 커넥션을 점유하지 않는다.
4. 채팅방 단위 Redisson 락은 그대로 유지해 같은 채팅방의 메시지 순서를 보존한다.

## 7. 개선 후 결과

| 실행 | 완료 시간 | 처리량 | 평균 | p50 | p95 | p99 | 최대 active | 최대 pending |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1,295ms | 15.444 req/s | 1,287ms | 1,287ms | 1,294ms | 1,294ms | 5 | 18 |
| 2 | 1,329ms | 15.049 req/s | 1,321ms | 1,320ms | 1,328ms | 1,328ms | 5 | 18 |
| 3 | 1,331ms | 15.026 req/s | 1,320ms | 1,322ms | 1,329ms | 1,331ms | 5 | 18 |

`maxPendingConnections`는 20개 요청이 동시에 DB 조회를 시작하는 순간의 짧은 최고값이라 전후 모두 18이었다. 그러나 개선 후에는 커넥션을 외부 호출 동안 유지하지 않아 대기가 지속되지 않았고, 전체 완료 시간과 p95가 약 1.33초로 수렴했다. 따라서 이 테스트에서는 순간 최고 pending보다 완료 시간과 지연시간 분포가 병목 해소를 더 잘 보여준다.

## 8. 정확성 검증

성능만 개선하고 메시지 저장을 잃지 않도록 회귀 테스트를 먼저 작성했다. (`ChatServiceTransactionBoundaryTest`, 기본 `./gradlew test`에 포함)

- 외부 호출(감정 분석) 시점에 실제 Spring 트랜잭션이 활성화되어 있으면 실패한다.
- LLM 호출이 실패해도 그 전에 저장한 사용자 메시지는 DB에 남아 있어야 한다.

수정 전에는 첫 번째 테스트가 실패했고, 트랜잭션 경계를 수정한 뒤 두 테스트 모두 통과했다.

측정에 사용한 부하 테스트 하네스(Testcontainers MySQL·Redis, 고정 지연 LLM 목 서버)는 로컬 전용으로 두고 저장소에는 포함하지 않았다.

## 9. 결과 해석의 한계

- 로컬 환경에서 실행한 서비스 계층 통합 테스트이며 HTTP 네트워크 직렬화 비용은 포함하지 않았다.
- 실제 Gemini 지연 대신 재현 가능한 고정 1초 지연을 사용했다.
- 요청 20개의 p95/p99 표본은 작으므로 운영 SLA를 의미하지 않는다.
- 결과는 절대적인 운영 처리량보다 트랜잭션 경계 변경의 상대 효과를 검증하는 데 목적이 있다.
- 기존에는 LLM 호출 실패 시 사용자 메시지 저장까지 함께 롤백될 수 있었지만, 개선 후에는 외부 호출 전에 저장된 사용자 메시지가 유지된다. 실패 메시지나 재처리 상태가 필요하다면 별도 신뢰성 개선 과제로 다뤄야 한다.
